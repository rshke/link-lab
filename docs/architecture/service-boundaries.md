# 服务边界与数据所有权

按执行权限、数据所有权和部署位置划分组件。模块 02 的验证逻辑集中在平台 API，模块 03 的排程、资源锁和运行状态机集中在工作流 Worker，避免首期将每个内部模块拆成微服务。

## 职责与数据

| 组件 | 负责与拥有的数据 | 对外边界 | 对应设计 |
| --- | --- | --- | --- |
| console | 页面与本地交互状态，无权威业务数据 | 平台 API、Agent API、孪生查询及实时流 | 01、06 |
| agent-service | 会话、检索上下文、草案生成记录、模型调用证据 | 接收会话请求，调用平台及孪生公开 API | 01 |
| platform-api | 草案及规格版本、验证报告、规则版本、审批、执行准入记录、能力快照 | 规格、验证、发布、运行及控制请求入口 | 02、07 |
| workflow-worker | 不可变计划、运行与步骤状态、资源预留、运行异常处置 | 消费已准入请求，调用设备网关，发布运行事实 | 03 |
| device-gateway | 设备发现和端点、实时能力注册、平台命令记录、关联映射、设备观察游标 | 提供平台内部命令接口，订阅 SiLA 2 状态并转换为事件 | 04、06 |
| twin-service | 设备、机器人、工位、样品及运行的查询投影，消费游标 | 查询、实时推送、事件回放 | 06 |
| adapters/sila2 | 厂商映射、本地命令去重与最终状态、断网缓冲 | 对网关暴露 SiLA 2，对本地 SDK、PLC 或 IPC 进行调用 | 04 |
| simulators | 虚拟时钟、设备状态、场景、故障与模拟结果 | 与真机相同的 SiLA 2 Feature；独立的模拟管理入口 | 05 |

能力注册表由网关维护设备当前能力与端点；平台 API 固化验证时使用的能力快照。工作流是运行状态和资源锁的唯一写入方，孪生中的 Run 只是查询投影。样品位置投影来自确认的设备与运行事实，不作为资源锁或安全互锁依据。

同一个 PostgreSQL 实例可以承载多个组件，但必须按组件划分 schema、迁移和访问权限，禁止跨 schema 直接读写。服务之间传递 ID 和版本化数据，不传 ORM 对象。事件流及审计存储属于部署基础设施；发布者负责事实语义，消费者只维护自己的游标与投影。

## 调用与事件流

```text
console ──→ agent-service ──→ platform-api
   │              └────────→ twin-service（只读）
   ├───────────────────────→ platform-api
   └───────────────────────→ twin-service

platform-api ──已准入请求──→ workflow-worker
workflow-worker ──命令──→ device-gateway ──SiLA 2──→ adapter 或 simulator
device-gateway ──设备事实──→ 事件总线 ──→ workflow-worker / twin-service
workflow-worker ──运行事实──→ 事件总线 ──→ twin-service
twin-service ──查询与实时推送──→ console
```

平台记录请求的幂等键及准入证据后，通过版本化消息或内部 API 交付工作流；消息交付时需使用事务性 outbox 等方式解决落库与发送的一致性。请求被受理不代表运行或设备动作完成。工作流检查规格与审批版本后生成不可变计划，设备实际执行结果由后续事件确认。

运行暂停、恢复和取消也由平台 API 校验授权后交给工作流。Agent 可以提交受权限约束的请求，但不能自行授予审批、降低验证错误等级或越过准入。

## 组件内部结构

各后端组件使用以下目录，具体语言的包结构可在实现时放入对应层：

```text
src/
  domain/             领域对象、不变量、状态转换
  application/        用例与事务边界
  ports/              用例依赖的存储、协议及消息接口
  infrastructure/     数据库、消息、协议客户端及外部 SDK 实现
  interfaces/         HTTP、事件消费、Worker 入口与组装
tests/                组件内单元及适配实现测试
```

源码依赖方向为 `application → domain / ports`、`infrastructure → ports / domain`、`interfaces → application`。入口组装代码可以引用基础设施以完成依赖注入；领域与应用逻辑不得反向依赖具体框架或驱动。

## 契约与共享代码

- `contracts/api/<service>/`：服务拥有的公开 API，后续采用 OpenAPI 或所选协议的正式定义。
- `contracts/schemas/`：ExperimentSpec、ValidatedSpec、ExecutionPlan、Command 和 CapabilitySnapshot 等交换格式；不包含业务实现。
- `contracts/events/`：统一信封和分领域事件。信封须包含事件标识、聚合标识、序号、发生及接收时间、关联与因果标识、版本和负载。
- `contracts/sila2/`：Feature Definition 与相关协议文件，是模拟器与真实适配器的共同依据。
- `packages/`：按需提取日志、追踪、契约客户端等技术库；领域规则不进入共享包。

契约测试统一验证模拟器和真机适配器的命令状态、进度、取消、幂等与重连行为。平台契约和端到端测试不得通过导入服务内部实现绕过公开边界。

## 首期部署与扩展

目录预留五个后端组件，但平台 API、设备网关和孪生投影可先在同一宿主中按模块运行。此时仍通过各自端口交互，不交叉访问数据。跨进程通信才使用网络 API 或消息代理，进程内事件总线不能承担跨进程交付。

Agent 与工作流可独立进程运行；三个模拟设备分别具有可配置的 SiLA 2 端点。未来真实适配器部署到设备 PC，只需替换网关注册端点，不改变上层业务语义。模拟管理接口仅面向本地开发及测试，生产平台不依赖其故障注入或 reset 接口。

首期不创建独立的验证器、排程器、知识服务、异常服务或 LADS 服务；出现明确部署、负载或团队边界后再通过架构决策拆分。
